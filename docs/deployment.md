# Deployment

The demo runs as a single EC2 instance running the compose stack behind Caddy,
with Terraform describing everything around it. This is AWS-as-a-VPS: cheap,
quick to stand up, and explicitly not highly available. See
[Tradeoffs](#tradeoffs) for what that buys and costs.

```
        │ https
        ▼
  ┌───────────────────────────────────────────────────┐
  │ EC2 t3.small  (public subnet, Elastic IP)         │
  │                                                   │
  │  caddy  ──▶  ui (nginx)  ──▶  api  ──▶  db        │
  │   TLS         SPA + proxy      agent    pgvector  │
  └───────────────────────────────────────────────────┘
        │                    │
        │ logs, metrics      │ models
        ▼                    ▼
   CloudWatch           Anthropic API
   → SNS → email
```

Shell access is AWS Systems Manager Session Manager, so **port 22 is closed and
there is no SSH key anywhere**. Deploys are an SSM command for the same reason.

## Cost

Roughly **$24/month**, steady state:

| Item | $/mo |
|---|---:|
| `t3.small` on-demand | 15.20 |
| Public IPv4 address | 3.65 |
| 30 GB gp3 EBS | 2.40 |
| Route53 hosted zone + health check | 1.25 |
| ~10 CloudWatch alarms | 1.00 |
| Logs, ECR, S3, snapshots | ~0.90 |

Plus the domain (~$14/yr) and Anthropic API usage, which the in-app budget
ceiling bounds. A 1-year no-upfront Savings Plan takes the instance to ~$11,
bringing the total to about $20.

## Prerequisites

1. **A domain you control.** Caddy gets a Let's Encrypt certificate for it, and
   Let's Encrypt will not issue for a bare IP. See
   [Without a domain](#without-a-domain) if that is a blocker.
2. AWS credentials with permission to create VPC, EC2, IAM, SSM, S3, ECR,
   CloudWatch, and Route53 resources.
3. An S3 bucket for Terraform state — Terraform cannot create the bucket that
   holds its own state.

## First deploy

```bash
aws s3 mb s3://your-tf-state-bucket --region us-east-1

cd terraform
cp backend.hcl.example backend.hcl              # point at that bucket
cp terraform.tfvars.example terraform.tfvars    # domain, emails, repo
terraform init -backend-config=backend.hcl
terraform apply
```

`terraform apply` prints a `next_steps` output. In full:

**1. Set the secrets.** Terraform creates the parameters with a placeholder and
ignores changes to their values, so real secrets never enter Terraform state:

```bash
aws ssm put-parameter --name /support-agent/anthropic_api_key \
  --type SecureString --overwrite --value 'sk-ant-...'
aws ssm put-parameter --name /support-agent/demo_admin_token \
  --type SecureString --overwrite --value "$(openssl rand -hex 16)"
```

The Postgres password is generated by Terraform and stored for you.

**2. Point DNS at the Elastic IP** from the `public_ip` output and wait for it
to resolve. Caddy cannot complete the ACME challenge before that, and it backs
off between retries — so getting this right first saves waiting.

**3. Confirm the SNS subscription** emailed to your `alert_email`. Until you
click that link, no alarm reaches you.

**4. Set `AWS_DEPLOY_ROLE`** in the repository's Actions *variables* to the
`deploy_role_arn` output, then run the `deploy` workflow. The stack does not
start until an image exists — on first boot the image tag is still `bootstrap`
and the instance deliberately stops short rather than failing on a pull.

**5. Set a spend limit on the Anthropic workspace** the key belongs to. The
in-app ceiling is the innermost of three limits and the only one an application
bug could bypass; this one it cannot.

## Deploying

Push to `main`, or run the workflow manually. It runs lint and the full test
suite first, then builds both images, pushes them to ECR tagged with the commit
SHA, records that tag in Parameter Store, re-runs `bootstrap.sh` on the
instance over SSM, and polls the public `/health/ready` until it answers.

Authentication is GitHub OIDC against a role scoped to this repository and the
`main` ref — no AWS keys are stored in GitHub.

The tag lives in Parameter Store rather than only in the workflow run so a
reboot comes back on the deployed version.

### Rolling back

```bash
aws ssm put-parameter --name /support-agent/image_tag --type String \
  --overwrite --value <previous-sha>
aws ssm send-command --instance-ids <id> --document-name AWS-RunShellScript \
  --parameters 'commands=["source /etc/support-agent.conf","/opt/support-agent/bootstrap.sh"]'
```

ECR keeps the last 10 images, so recent SHAs are available to roll back to.

### Changing runtime config

`docker-compose.prod.yml` and the `Caddyfile` are owned by Terraform and served
to the instance from S3. Edit them in the repo, `terraform apply`, then deploy
(or reboot) to pick them up. They are deliberately not edited on the box.

## Operations

```bash
# Shell — no SSH key, no open port
aws ssm start-session --target <instance-id>

# Logs
aws logs tail /support-agent/containers --follow
aws logs tail /support-agent/containers --follow --filter-pattern '{ $.level = "error" }'

# Current model spend
aws logs tail /support-agent/containers --filter-pattern '{ $.event = "budget_snapshot" }'

# On the box
cd /opt/support-agent && docker compose -f docker-compose.prod.yml ps
cat /var/log/support-agent-bootstrap.log   # first-boot output
```

### Restoring the database

Nightly `pg_dump` output lands in `s3://<config-bucket>/backups/`, retained 14
days. EBS snapshots (daily, 7 days) cover losing the volume itself.

```bash
aws s3 cp s3://<bucket>/backups/support_agent-<stamp>.sql.gz - \
  | gunzip | docker compose -f docker-compose.prod.yml exec -T db psql -U support support_agent
```

Losing the database is not catastrophic by design: `scripts/seed_db.py` runs on
every boot and every deploy, so the demo data rebuilds itself. Only
visitor-created tickets are lost.

## Alarms

All route to one SNS topic and your email.

| Alarm | Fires when |
|---|---|
| `spend-warning` / `spend-exhausted` | Model spend crosses 60% / 100% of the daily ceiling |
| AWS Budgets (actual + forecast) | Infrastructure cost passes the monthly threshold |
| `unreachable` | Route53 fails the public health check three times |
| `status-check-failed` | EC2 instance or host check fails |
| `cpu-high` / `memory-high` / `disk-high` | 80% / 85% / 80% sustained |
| `error-rate` | More than 10 error log lines in 5 minutes |
| `agent-run-failures` | More than 3 failed background runs in 15 minutes |

`memory-high` is the one most likely to fire first: Postgres, the ONNX
embedding runtime, and the agent share 2 GB. Memory and disk come from the
CloudWatch agent — EC2 does not publish them natively.

Spend alarms treat missing data as *not* breaching, because no datapoints means
the app is not reporting, which is the uptime alarm's job.

## Guardrails on the public surface

Set in `docker-compose.prod.yml` and enforced by the app:

- **Rate limits** per client IP, derived from `X-Forwarded-For` counting
  `TRUSTED_PROXY_HOPS=2` in from the right (Caddy appends the client, nginx
  then appends Caddy). Counting from the right is what stops a caller forging
  a prefix to get a fresh bucket.
- **Daily spend ceiling** (`DAILY_BUDGET_USD`) refusing new agent runs with 429
  once 24 hours of recorded cost passes it. Reads stay available.
- **Concurrency bound** (`MAX_CONCURRENT_RUNS=2`) so a burst of submissions
  cannot become a burst of concurrent model calls on a 2 vCPU box.
- **`/mock-api/*` returns 403** at Caddy and again in nginx. It issues refunds
  without passing the eligibility engine or the approval gate. The agent is
  unaffected — it reaches the order API container-to-container.
- **`DELETE /api/tickets/{id}` requires `X-Demo-Token`.** Submitting and
  approving stay open on purpose; the human-in-the-loop flow is the thing worth
  showing.

## Without a domain

Let's Encrypt will not issue for a bare IP, so Caddy cannot help. Put a
CloudFront distribution in front of the instance instead: it provides free
HTTPS on a `*.cloudfront.net` hostname with a plain-HTTP origin, and the
security group can be narrowed to the
`com.amazonaws.global.cloudfront.origin-facing` managed prefix list so only
CloudFront can reach port 80. Drop the `caddy` service, publish `ui` on port 80,
and move the `/mock-api/*` block into nginx (it is already there). You trade
~$14/yr for an ugly hostname.

## Tradeoffs

What this shape deliberately does not give you:

- **No high availability.** One instance, one AZ. A terminated instance does
  not come back on its own; `terraform apply` builds a new one, and the
  database rebuilds from seed.
- **No managed database.** Postgres is a container on the instance's volume.
  Backups are the nightly dump and EBS snapshots, not RDS point-in-time
  recovery.
- **Rate limit counters are in memory**, so they are accurate only while
  exactly one API container runs — which is this topology. More than one
  replica needs a shared backend.
- **Deploys have a few seconds of downtime** while containers restart.

Each is a deliberate trade for cost. The ECS/Fargate + ALB + RDS alternative
fixes all four for roughly $55/month.
